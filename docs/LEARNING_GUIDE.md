# Spike 학습과 교체 안내

먼저 [실행 안내](RUN_DEMO.md)의 시연을 한 번 해본 뒤 코드 흐름을 따라간다. 코드를 전부 읽기보다 한 결과가 왜 나왔는지 원본부터 추적하는 방식으로 살펴본다.

## 1. 후보와 결정은 다른 자료다

모호한 사례를 분석하고 JSON을 내보낸다. `observations`에는 입력 영역과 6/8 문자 후보가 그대로 있다. `baseline`은 맥락을 사용하지 않은 해석, `contextual`은 같은 후보에 작업 맥락을 적용한 판단이다. `field_origins`는 시각 후보·계획·이력·사람 수정 중 무엇으로 값을 정했는지 설명한다.

[`engine.py`](../src/contextweld/engine.py)의 `parse_observations`, `decide`를 읽는다. `normalize`는 시연 라벨을 구조화한다. `decide`는 이미지 부재와 계획 부재의 일치, 누락·충돌, 적용 범위를 확인한 뒤 프로그램 후보를 연결한다. 후보를 좁힌 경우에도 원본 확인 요청을 남긴다.

**실습:** 모호한 사례의 계획 치수를 비우고 분석한다. 이후 다른 부재번호를 입력해 분석한다. 맥락이 부족하거나 다른 부재의 계획일 때 왜 보류하는지 `blockers`로 확인한다. 이 연습에서는 확인 이력이 이미 저장돼 있으면 결과가 달라질 수 있다.

## 2. 사람 확인은 근거와 버전을 남긴다

[`store.py`](../src/contextweld/store.py)의 `create`와 `review`를 읽는다. SQLite는 입력 관측, 작업계획, 두 해석 결과, 규칙 버전, 분석 당시의 이력 목록을 저장한다. 수정 시 원본과 맥락을 덮어쓰지 않고 수정값과 이유를 별도 기록한다. 동시에 열린 오래된 화면의 수정은 분석 `revision`으로 거부한다.

확인된 이력은 같은 부재·이음부·재질·두께·자세·계획 버전·규칙 버전에서만 쓰며, 새 인식 후보 안에 있는 값만 좁힌다. 모델 재학습은 수행하지 않는다. 분석을 만드는 시점의 이력을 사용하므로 나중에 확인된 정보를 적용하려면 새로 분석해야 한다.

**실습:** 모호한 결과를 확인한 뒤 이력 사례를 실행한다. 계획 버전을 바꾸고 재분석해 이전 확인이 적용되지 않는지 본다. 충돌 사례를 수정한 JSON에서는 원래 후보 8, 수정값 6, 확인 이유가 함께 남는지 확인한다.

## 3. 화면과 API는 판단 엔진에 연결한다

[`server.py`](../src/contextweld/server.py)의 `/api/analyze`, `/api/review`, `/api/upload` 처리를 읽고 [`app.js`](../src/contextweld/web/app.js)의 같은 이름 함수를 살펴본다. 시연 사례는 서버가 소유한 후보를 사용하고, 업로드는 실제 OCR 결과를 보관한 뒤 분석한다. 클라이언트가 결과를 임의로 승인하도록 서버 검증을 생략하지 않는다.

[`test_engine.py`](../tests/test_engine.py)는 판단과 저장의 주요 경계를, [`test_server.py`](../tests/test_server.py)는 HTTP 요청부터 저장·재사용까지 연결을 검증한다. 제품 성능평가를 대신하는 테스트는 아니다.

## 4. 멘토링 후 교체할 지점

| 새로 확보한 정보 | 우선 바꿀 지점 | 유지할 것 |
|---|---|---|
| 실제 표기 사진과 약어 사전 | `ocr.py`, `parse_observations`, 사례 데이터 | 영역·후보·출처와 원본 보존 |
| 조선소 부재·이음부 식별 체계 | 맥락 입력, `trusted_identity`, `memory_scope` | 다른 작업의 맥락을 적용하지 않는 검증 |
| 표기 규칙·작업 기준 문서 | `search_evidence`, knowledge 데이터 | 문서 출처·버전·적용 범위 |
| 승인된 WPS와 공정 적용 규칙 | recipes와 적용 범위 판정 | 근거 없는 전류·전압·속도 생성 금지 |
| 실제 불확실성·확인 절차 | 보류·확인 정책과 화면 | 누가 무엇을 왜 수정했는지 이력 |
| 실제 평가 사진과 전문가 정답 | 별도 평가 데이터와 측정 도구 | 개발 예시와 평가셋 분리 |

**첫 멘토링 이후 우선순위:** 장면 하나의 실제 입력·정답·기준을 확보하고 그 장면의 파서·규칙부터 고친다. 이후 필요에 따라 VLM·문서 검색을 연결한다. 출력 형식과 원본·판단·확인 분리를 유지하면 화면과 저장소를 재사용할 수 있다. 어느 지점까지 재사용할지는 새 자료의 표기·공정 체계에 따라 달라진다.

## 설명할 때 구분할 주장

현재 보여줄 수 있는 것은 후보·맥락·시연 기준·사람 확인을 연결한 동작이다. 화면의 전후 비교는 같은 문자 후보를 고정한 기능 비교다. OCR 정확도 향상, 현장 해석 정확도, 용접 품질, 작업시간 절감은 아직 측정하지 않았다. 실제 모델 출력은 업로드 경로의 Apple Vision OCR이며, 예시 시연의 복수 후보는 작성된 데이터다. 규칙 조회는 키워드 검색이고 임베딩 RAG·VLM·현장 WPS 추천은 아직 구현하지 않았다.
