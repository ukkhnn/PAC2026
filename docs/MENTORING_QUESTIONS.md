## 1. 이번에 질문하는 근본적인 이유

**먼저 확인할 것은 ‘글씨를 얼마나 잘 읽는가’보다 ‘현장에서 누가, 어떤 결정을 위해, 그 글씨를 읽는가’다.**

팀의 기존 설계는 표기를 읽고 작업 맥락·기준을 대조해 작업 또는 조건 후보를 제시하는 구조다. 그런데 설계 데이터가 이미 로봇 작업으로 이어지는 현장이라면, 사람이 모든 수치를 표기에서 읽어 다시 입력한다는 전제가 맞지 않을 수 있다. 어떤 작업 데이터를 선택할지 결정하거나, 실물과 기존 데이터의 차이를 확인하는 일이 더 중요한지 확인해야 한다.

하위 페이지가 참고한 MHI 기술리뷰에는 CAD 기반 작업 데이터 생성과 조건 DB 활용, 작업자의 대상 데이터 선택, 현장 차이에 따른 태블릿 수정 사례가 나온다. 이는 **2013년 MHI의 특정 적용 사례**이며 이번 미션의 현장과 동일하다는 뜻은 아니다. [MHI 기술리뷰, 2013년 6월, §2.4·§3.1·§3.2](https://www.mhi.com/technology/review/sites/g/files/jwhtju2326/files/tr/pdf/e502/e502056.pdf)

## 3. 질문별 배경·필요성·후속 결정

아래의 ‘답변 후 결정’은 팀의 검토 방향이다. 특정 답변을 유도하거나 현장 사정을 미리 사실로 정한 내용이 아니다.

### 1. 어느 현장에서, 어떤 판단에 표기가 필요한가?

**질문 텍스트**

> 이번 과제가 가장 우선적으로 대상으로 하는 공정과 로봇 운용 방식은 무엇인가요? 그 현장에서 작업자가 철판이나 부재의 표기를 보고 어떤 결정을 하는지, 실제 작업 한 건을 기준으로 설명해 주실 수 있을까요?

**이어 물을 말**

> 설계 데이터를 이미 불러온 상황에서도 표기를 확인하나요? 확인한다면 어떤 결정을 위해서이고, 확인하지 않는다면 현재 방식에서 남아 있는 어려움은 무엇인가요?

**질문하게 된 배경** — 상위 페이지는 표기 해석에서 작업·조건으로 이어지는 흐름을 다루고, 하위 페이지는 이미 데이터가 연결된 공정에서도 표기 인식이 필요한지 되묻는다. 두 문제의식 사이에서 실제 적용 장면을 먼저 고정할 필요가 있다.

**왜 필요한가** — 해결할 일이 없는 단계에 기능을 붙이는 것을 피하고, 사진을 읽은 결과가 누구의 어떤 판단을 돕는지 명확히 하기 위해서다.

**답변에서 확보할 것** — 대상 공정·로봇·사용자, 표기를 보는 시점, 그때 내리는 결정, 현재의 불편, 적용되지 않는 예외.

**답변 후 결정** — 작업 선택이 문제라면 실물과 데이터의 연결을, 현장 차이가 문제라면 불일치 확인을 우선 검토한다. 해당 공정에 표기 관련 문제가 없다면 적용 대상을 다시 조사한다. 곧바로 다른 공정이나 미래 로봇에 수요가 있다고 가정하지 않는다.

원문 연결: 하위 R1·R3.

### 2. 작업지시는 어떤 경로로 전달되고, 사람은 무엇을 하는가?

**질문 텍스트**

> 대표 작업 하나가 설계 단계에서 실제 로봇 실행까지 전달되는 순서를 설명해 주실 수 있을까요? 각 단계에서 작업자가 직접 고르는 정보, 새로 입력하는 정보, 수정하는 정보가 무엇인지 알고 싶습니다.

**이어 물을 말**

> 가능하다면 실제 입력 화면이나 작업지시서에서 해당 항목을 보여주실 수 있을까요? 자료 공유가 어렵다면 항목 이름만 설명해 주셔도 됩니다.

**질문하게 된 배경** — 표기를 읽는 기능을 만들더라도, 그 결과가 기존 작업 흐름의 어디에 들어가는지가 아직 확정되지 않았다. 하위 페이지는 ‘선택·입력·수정’을 구분해 이 연결 지점을 찾으려 한다.

**왜 필요한가** — 우리가 줄이려는 사람의 행동과 비교 대상을 정하기 위해서다. 실제 입력이 없는 항목을 자동 입력하는 시연은 현장 효과를 설명하기 어렵다.

**답변에서 확보할 것** — 단계별 입력·출력, 사용하는 화면·문서, 담당자, 선택 단위, 수정 내용, 작업 시작 조건.

**답변 후 결정** — 기존 화면 앞에서 후보를 추천할지, 선택한 작업을 대조할지, 변경 내역을 확인할지 결정한다. 현장 사례를 ‘원래 표기 → 추가 확인 정보 → 최종 결정’ 순서로 기록한다.

원문 연결: 상위 Q3, 하위 R2.

### 3. 표기는 무엇을 뜻하며, 원래 정보인가 변경 지시인가?

**질문 텍스트**

> 현장 표기에 주로 어떤 정보가 담기나요? 실제 표기 하나를 예로 들어 각 문자·숫자·기호가 무엇을 뜻하는지 설명해 주실 수 있을까요? 특히 수기 표기가 도면의 정보를 옮긴 것인지, 대상을 식별하는 것인지, 현장에서 추가하거나 바꾼 지시인지 구분하고 싶습니다.

**이어 물을 말**

> 같은 약어나 기호가 공정·팀에 따라 다르게 쓰이나요? 표기는 누가 언제 작성하고, 수정·취소된 표기는 어떻게 구별하나요?

**질문하게 된 배경** — 하위 페이지에는 ‘표기는 실물과 데이터를 잇는 열쇠일 수 있다’는 관점이 있다. 다만 수기 표기에 새로운 지시가 포함된다면 기존 데이터와 맞추는 것만으로는 의미를 해석할 수 없다.

**왜 필요한가** — 인식할 항목과 표기 사전을 정하고, 원문을 기존 데이터에 맞춰 잘못 고치는 일을 막기 위해서다. 표기를 전부 같은 종류로 취급하면 식별 정보와 변경 지시를 혼동할 수 있다.

**답변에서 확보할 것** — 원본 표기와 뜻, 작성자·시점, 표기 유형, 적용 범위, 혼동하기 쉬운 예, 변경·취소 표시.

**답변 후 결정** — 식별 표기는 연결 후보를 찾는 데, 작업 지시는 의미 해석에, 변경 표기는 별도 확인 절차에 활용하는 방안을 검토한다. 일부 사례만으로 전체 표기가 사본이라고 확정하지 않는다.

원문 연결: 하위 Q4·K1.

### 4. 숙련자는 애매한 표기를 무엇으로 판단하는가?

**질문 텍스트**

> 글씨가 흐리거나 여러 의미로 읽히는 실제 사례가 있을까요? 그때 숙련 작업자는 무엇부터 확인하고, 어떤 정보를 보고 최종 판단했는지 순서대로 설명해 주실 수 있을까요?

**이어 물을 말**

> 주변 표기, 도면, 이전 작업 기록 등을 봐도 결론이 안 나면 어떻게 하나요? 참고 정보가 오래됐거나 다른 작업의 정보인지는 어떻게 확인하나요?

**질문하게 된 배경** — 팀은 작업 맥락을 활용하려 하지만, 어떤 정보가 실제 판단에 도움이 되는지는 현장 사례로 확인해야 한다. 하위 페이지의 숙련자 판단 질문을 상위 페이지의 ‘판단 과정 한 건’과 연결했다.

**왜 필요한가** — 유효한 맥락과 임의 추측을 구분하고, 후보를 좁힐 기준과 판단을 멈출 기준을 정하기 위해서다.

**답변에서 확보할 것** — 처음 가능한 해석, 확인한 정보의 순서와 출처, 최종 결정 근거, 판단 불가 사례.

**답변 후 결정** — 확보 가능한 정보부터 대조하고, 다른 대상·오래된 버전의 정보는 구분한다. 숙련자의 설명 한 건을 곧바로 모든 작업에 적용되는 규칙으로 만들지는 않는다.

원문 연결: 상위 Q3, 하위 K4.

### 5. 사진 속 대상과 실제 작업 데이터를 어떻게 연결하는가?

**질문 텍스트**

> 사진을 찍는 시점에 시스템이나 작업자가 이 부재 또는 용접부가 어떤 작업 대상인지 알고 있나요? 알고 있다면 어떤 식별자나 선택 절차로 작업지시·도면과 연결하나요?

**이어 물을 말**

> 같은 번호가 다른 블록이나 작업에 반복될 수 있나요? 자동 연결이 어렵다면 작업자가 블록이나 작업을 먼저 선택하는 방식은 현실적으로 가능한가요?

**질문하게 된 배경** — 상위 Q4는 사진을 특정 작업과 연결할 수 있는지 묻는다. 맥락을 활용하려면 정보가 있다는 사실뿐 아니라 그 정보가 사진 속 대상의 것인지 확인할 수 있어야 한다.

**왜 필요한가** — 문자를 정확히 읽고도 다른 부재의 작업지시를 가져오는 오류를 막기 위해서다. 연결이 틀리면 이후 대조와 조건 후보도 함께 잘못될 수 있다.

**답변에서 확보할 것** — 식별 단위와 고유 범위, 연결 키, 중복 가능성, 작업자 선택 가능 여부, 연결을 검증하는 방법.

**답변 후 결정** — 자동 연결, 작업자 선택 후 대조, 제한된 후보 중 확인 중 가능한 방식을 고른다. 연결 정보가 없으면 작업별 조건 추천 범위를 줄인다. 원문의 ‘외부 연결이 없으면 진행 불가’로 바로 결론내리지 않는다.

원문 연결: 상위 Q4, 하위 R2·Q1.

### 6. 어떤 설계·작업 데이터를 실제 입력으로 쓸 수 있는가?

**질문 텍스트**

> 이번 과제에서 저희가 입력으로 사용할 수 있는 설계·작업계획 정보는 무엇인가요? 예를 들어 부재 목록, 재질·판 두께, 이음 형태, 각장, 자세, 작업 순서 중 실제로 제공되거나 연결 가능한 항목을 알고 싶습니다.

**이어 물을 말**

> 그 정보는 어떤 파일이나 시스템에 있고, 언제 갱신되나요? 실제 제공이 어려운 항목을 모의 데이터로 가정해 시연하는 것은 허용되나요?

**질문하게 된 배경** — 하위 Q1은 설계 데이터 사용 가능 여부로 구현 방향을 나눈다. 그러나 ‘현장에 존재함’, ‘우리 시스템이 접근 가능함’, ‘대회에서 가정해도 됨’은 각각 별도 확인이 필요하다.

**왜 필요한가** — 받을 수 없는 정보를 필수 입력으로 설계하는 일을 피하고, 실제 데이터 기반 기능과 시연용 가정을 구분하기 위해서다.

**답변에서 확보할 것** — 항목명, 파일 형식, 대상 식별자, 버전·시각, 제공 방식, 접근 범위, 모의 데이터 허용 여부.

**답변 후 결정 — 당시 검토안** — 실제 사용할 수 있는 항목만 대조에 포함한다. 외부 데이터가 없다면 표기 자체의 해석과 작업자 확인 중심으로 범위를 재검토한다. 과거 확인 기록의 재사용은 당시 검토한 확장안이며 현재 데모의 자동 참조 기능으로 구현하지 않는다.

원문 연결: 하위 Q1, 상위 Q4.

### 7. 사진·정답·규칙을 무엇부터 언제 받을 수 있는가?

**질문 텍스트**

> 실제 사진과 그 표기의 의미, 관련 작업 정보, 판단 근거가 함께 연결된 사례를 받을 수 있을까요? 우선 한 건이라도 좋습니다. 추가로 제공 가능한 자료 종류와 대략적인 규모, 제공 시점·형식도 알고 싶습니다.

**이어 물을 말**

> 정답은 누가 검토한 것인지 확인할 수 있을까요? 사진이나 문서를 개발, 외부 AI 처리, 발표 화면, 공개 저장소에 각각 사용할 수 있는지도 구분해서 알려주시면 좋겠습니다. 원본 공유가 어렵다면 비식별 예시나 스케치로 설명해 주실 수 있을까요?

**질문하게 된 배경** — 상위 Q1과 하위 Q2는 모두 자료 제공을 묻는다. 팀 문서에는 실제 현장 데이터·적용 기준·독립된 평가 자료가 아직 확보되지 않았다고 기록돼 있다.

**왜 필요한가** — 사진만으로는 의미 해석이나 조건 후보가 맞는지 평가하기 어렵다. 같은 작업의 사진·뜻·근거를 함께 받아야 구현과 검증을 연결할 수 있다.

**답변에서 확보할 것** — 자료 목록, 사진과 정답의 대응 관계, 검토자, 제공일·담당 창구, 사용 범위, 공개 가능 여부.

**답변 후 결정** — 연결된 사례로 첫 구현 장면을 정하고, 가능하다면 개발 사례와 별도 평가 사례를 확보한다. 실제 자료가 없으면 합성·시연 자료임을 명시하고 현장 정확도를 주장하지 않는다.

원문 연결: 상위 Q1·Q3, 하위 Q2.

### 8. 이번 대회에서 반드시 보여줘야 하는 결과는 어디까지인가?

**질문 텍스트**

> 이번 미션의 최소 결과물과 필수 출력 항목을 확인하고 싶습니다. 표기의 의미와 작업 후보를 보여주는 수준, 조건 DB나 WPS와 연결하는 수준, 전류·전압 같은 설정값을 출력하는 수준, 실제 로봇에 전달해 실행하는 수준 중 어디까지가 필수인가요?

**이어 물을 말**

> 작업 위치·방향·순서는 이미지 위 표시나 구조화된 정보로 제시하면 되는지, 로봇 좌표나 경로까지 필요한지도 알려주실 수 있을까요? 실행 시제품·영상·발표 자료는 각각 어떻게 평가하나요?

**질문하게 된 배경** — 상위 Q2와 하위 Q3에는 ‘후보 추천’과 ‘자동 설정’의 범위가 혼재한다는 문제의식이 있다. 이 질문지는 그 표현을 운영진에게 확인하기 위한 것이며 공식 필수 요건을 자체 확정하지 않는다.

**왜 필요한가** — 출력 수준마다 필요한 데이터와 검증 방식이 달라진다. 개발 범위를 정하고 필수 결과물을 빠뜨리지 않기 위해 먼저 확인해야 한다.

**답변에서 확보할 것** — 필수·선택 출력, 실제 제어 필요 여부, 시연 방식, 평가 기준, 관련 공식 안내.

**답변 후 결정** — 확인된 요구 범위에 맞춰 구현을 고정한다. 실제 설정값이 필요하면 해당 값의 기준 자료와 검증 방법을 함께 요청한다.

원문 연결: 상위 Q2, 하위 Q3·E1. 우선 확인 대상: 운영진·미션 담당자.

### 9. 용접조건은 어떤 정보와 근거로 결정하는가?

**질문 텍스트**

> 실제 현장에서는 용접조건을 어떤 절차로 결정하나요? 한 사례에서 어떤 정보를 입력으로 보고, 어떤 기준표나 조건 DB, WPS를 참고해 최종 작업 조건을 정하는지 설명해 주실 수 있을까요?

**이어 물을 말**

> 필요한 정보 중 표기에서 읽어야 하는 것, 설계에서 가져오는 것, 센서로 측정하는 것은 각각 무엇인가요? WPS와 로봇 프로그램·조건 DB는 어떻게 연결되고, 적용 가능한 조건이 없거나 여러 개면 어떻게 처리하나요?

**질문하게 된 배경** — 하위 R7은 조건 DB와 WPS의 관계, 센서값과 표기 정보의 역할을 구분하려 한다. 상위 Q5에는 제목만 있어 실제 질문 문장과 확보할 정보가 보완돼야 했다.

**왜 필요한가** — 표기를 읽는 것과 용접조건을 정하는 것 사이에 어떤 근거가 필요한지 확인하기 위해서다. 단순 조회인지 계산·보정·승인이 함께 필요한지에 따라 구현이 달라진다.

**답변에서 확보할 것** — 입력 항목과 출처, 적용 범위·버전, 조건 결정 절차, 예외 처리, 최종 승인 단계.

**답변 후 결정** — 현장이 사용하는 근거와 결정 절차에 맞춰 후보를 제시한다. 표기만으로 판단할 수 없는 설정값은 임의로 채우지 않는다. 센서값을 직접 추정할지와 외부에서 입력받을지는 별도로 정한다.

원문 연결: 상위 Q5, 하위 R7·Q3.

### 10. 표기·도면·작업계획이 다르면 무엇을 확인하는가?

**질문 텍스트**

> 현장 표기와 도면이나 작업계획이 서로 다른 사례가 있나요? 그때 단순 오기인지, 승인된 변경인지, 아직 반영되지 않은 정보인지 어떻게 구분하고 누가 최종 판단하나요?

**이어 물을 말**

> 어떤 문서의 버전이나 변경 기록을 확인하나요? 해결될 때까지 해당 작업은 어떻게 처리하고, 최종 결정은 어디에 기록하나요?

**질문하게 된 배경** — 설계 정보를 표기의 정답으로 간주하면 현장의 유효한 변경 지시를 지워버릴 수 있다. 반대로 수기 표기를 항상 우선하면 승인되지 않은 변경을 따를 수 있다.

**왜 필요한가** — 불일치를 찾은 뒤 무엇을 해야 하는지 정하기 위해서다. 탐지뿐 아니라 확인 주체·근거·보류 범위·해결 기록이 필요하다.

**답변에서 확보할 것** — 실제 충돌 사례, 원인, 빈도, 확인 자료, 판단 권한, 대기·재개 절차, 기록 위치.

**답변 후 결정** — 모든 충돌에 고정된 우선순위를 강제하지 않고, 현장에서 확인한 적용 규칙과 승인 절차를 반영한다. 해결 전 후보와 근거를 함께 보여주는 방안을 검토한다.

원문 연결: 상위 Q5, 하위 K2.

### 11. 어떤 오류가 자주 생기고, 어떤 오류의 영향이 큰가?

**질문 텍스트**

> 표기를 잘못 읽거나 다른 작업 데이터를 선택해 문제가 생긴 사례가 있을까요? 자주 발생하는 실수와, 드물지만 영향이 큰 실수를 나눠서 듣고 싶습니다. 각각 어느 단계에서 발견되고 어떻게 복구하나요?

**이어 물을 말**

> 공개 가능한 범위에서 발생 빈도, 재확인·재작업 시간, 작업 중단 영향을 대략적으로 알려주실 수 있을까요? 현재 절차로 이미 잘 걸러지는 오류도 궁금합니다.

**질문하게 된 배경** — 하위 R6과 K3는 잘못된 선택이나 해석이 실제로 어떤 문제를 일으키는지 묻는다. 단순 문자 정확도만으로는 오류의 중요도를 구분할 수 없다.

**왜 필요한가** — 먼저 막아야 할 오류와 실제 추가 효과가 있는 지점을 정하기 위해서다. 이미 다른 절차가 막는 오류를 우리 시스템만의 효과로 계산하지 않도록 한다.

**답변에서 확보할 것** — 오류 유형, 발견 단계, 기존 방어 절차, 빈도와 영향의 근거, 복구 방식.

**답변 후 결정** — 영향이 큰 항목은 별도 오류 지표와 확인 절차로 다룬다. 비용·시간은 현장 답변의 추정인지 실제 기록인지 구분해 기록한다.

원문 연결: 하위 R6·K3.

### 12. 사람의 시간은 어디에 들고, 확인 절차를 어디에 넣을 수 있는가?

**질문 텍스트**

> 대표 작업의 준비부터 용접·검사까지 실제 순서를 설명해 주실 수 있을까요? 각 단계에서 누가 개입하고, 사람이 직접 작업하는 시간과 기다리는 시간이 각각 어느 정도인지 알고 싶습니다. 가장 자주 막히는 단계는 어디인가요?

**이어 물을 말**

> 표기 촬영이나 결과 확인을 추가한다면 어느 시점이 가장 자연스러울까요? 기존 작업과 동시에 처리할 수 있는지, 별도 대기가 생기는지도 궁금합니다.

**질문하게 된 배경** — 하위 R5는 공정 전체의 사람 개입 시간을 묻는다. 원문에 제시된 ‘마킹 → 취부 → 배치 → 호출 → 스캔 → 용접 → 검사’는 확인할 예시 순서이며 모든 현장의 고정 순서로 사용하지 않는다.

**왜 필요한가** — 인식 속도가 빨라도 촬영·확인 절차가 추가되면 실제 업무 시간이 늘 수 있다. 현재 방식과 비교할 기준을 얻기 위해서다.

**답변에서 확보할 것** — 실제 단계, 담당자, 직접 작업시간, 대기시간, 반복 빈도, 병목, 확인을 넣을 수 있는 시점.

**답변 후 결정** — 줄일 수 있는 단계에만 개선 목표를 세우고 새로 생기는 시간도 포함한다. 다른 사례의 스캔 시간 전체를 우리 처리에 사용할 수 있다고 가정하지 않는다.

원문 연결: 하위 R5.

### 13. 누가 확정하고, 확인 요청을 얼마나 처리할 수 있는가?

**질문 텍스트**

> 표기 해석이나 조건 후보를 시스템이 제시했을 때, 현장에서는 누가 어떤 근거를 보고 확정하는 것이 맞을까요? 작업 시작 전에 반드시 거쳐야 하는 확인 단계가 있나요?

**이어 물을 말**

> 한 사람이 여러 작업이나 로봇을 맡는다면 확인 요청이 어느 정도 빈도로 오는 것이 현실적인가요? 장갑을 낀 상태에서 어떤 화면이나 입력 방식이 편하고, 답변이 늦어질 때는 어떻게 처리해야 할까요?

> 한 번 확인한 내용은 같은 작업의 후속 단계에서도 사용할 수 있나요? 대상이나 도면·계획 버전이 바뀌면 다시 확인해야 하는 기준이 있나요?

**질문하게 된 배경** — 하위 K5는 확정 주체를, R9는 확인 요청을 감당할 수 있는 수준을 묻는다. 팀의 기존 설계에는 확인 이력 활용도 있어 재사용 범위를 함께 묻도록 보완했다.

**왜 필요한가** — ‘애매하면 사람에게 묻는다’가 실제로 운영 가능한 기능이 되려면 담당자, 요청 빈도, 확인 근거, 미응답 처리가 정해져야 한다. 이력 재사용으로 오래된 판단이 반복 적용되는 것도 막아야 한다.

**답변에서 확보할 것** — 승인 역할·권한, 필요한 근거, 확인 소요시간·빈도, 미응답 처리, 이력 유효 범위와 재확인 조건.

**답변 후 결정** — 요청을 모아 보여줄지, 작업 직전에 확인할지, 어떤 선택지를 줄지 결정한다. 확인 부담이 크다는 이유만으로 확정 기준을 낮추지 않고 대상 축소·입력 개선·처리 절차를 먼저 검토한다.

원문 연결: 하위 K5·R9, 하위 Q1의 Work Memory. 이력 유효 범위는 기존 프로젝트 설계를 반영한 보완 질문.

2026-10-10 현재 구분: 위 질문은 미래 현장 조사용이다. 현재는 수정 저장과 명시적 별도 재검토만 허용하며, 같은 대상이라는 이유로 과거 수정이나 승인을 자동 상속하지 않는다.

### 14. 어떻게 촬영하고, 결과는 어디로 전달하는가?

**질문 텍스트**

> 이번 과제에서 표기 사진은 누가 어떤 장비로 촬영하는 상황을 생각하시나요? 촬영 거리·각도·조명이나 재촬영 가능 여부처럼 먼저 고려해야 할 조건이 있을까요?

**이어 물을 말**

> 해석 결과는 사람이 보는 화면에서 끝나나요, 아니면 기존 작업 시스템이나 로봇 쪽으로 전달해야 하나요? 전달한다면 받는 시스템과 필수 항목, 예시 파일 형식을 알 수 있을까요?

**질문하게 된 배경** — 하위 R8은 입력 장비와 출력 형식을 묻는다. 실제 연결을 요구하는지와 단지 연결 가능한 데이터 구조를 요구하는지는 다를 수 있다.

**왜 필요한가** — 촬영 조건에 맞는 인식 방법을 고르고, 결과를 기존 업무에서 사용할 수 있는 형태로 만들기 위해서다.

**답변에서 확보할 것** — 촬영 주체·장비·환경, 재촬영 가능 여부, 결과 수신 주체, 필수 필드, 단위·좌표계, 예시 형식.

**답변 후 결정** — 실제 입력 조건으로 시험하고 요구 형식으로 내보낸다. 구조화 파일 생성과 로봇에서의 실행 검증을 구분한다.

원문 연결: 하위 R8, 상위 Q2.

### 15. 가장 먼저 도입할 대상과 효과는 무엇인가?

**질문 텍스트**

> 표기를 읽고 작업 정보와 대조하는 부담이 큰 공정이나 현장은 어디인가요? 반대로 기존 데이터 연결만으로 충분해서 이 기능이 거의 필요하지 않은 곳도 알려주실 수 있을까요?

**이어 물을 말**

> 우선 한 곳에서 시험한다면 누가 사용하고 누가 도입 여부를 판단할까요? 그 대상의 작업량과, 도입을 검토할 만큼 개선돼야 하는 시간·오류·재작업 수준을 대략적으로 알고 싶습니다.

**질문하게 된 배경** — 하위 R4는 표기에 의존하는 현장의 범위와 물량을 묻는다. 다만 데이터 연계가 적다는 이유만으로 특정 공정·협력사에 수요가 있다고 단정할 수는 없다.

**왜 필요한가** — 발표에서 ‘누가 왜 쓸 것인가’를 구체화하고, 실제 실증 가능한 첫 대상을 정하기 위해서다.

**답변에서 확보할 것** — 우선 대상과 제외 대상, 사용자·도입 판단자, 작업량의 단위와 기간, 현행 대안, 도입 판단 기준.

**답변 후 결정** — 해당 범위에서 확인된 문제와 물량만 근거로 사용한다. 수요가 작으면 문제·대상을 재검토하며, 미래 로봇 시장의 필요성이 자동으로 입증됐다고 해석하지 않는다.

원문 연결: 하위 R4. 사용자·도입 판단자 구분은 실증 계획을 위한 보완 질문.

### 16. 정확도·자동 처리·사람 확인을 어떻게 함께 평가하는가?

**질문 텍스트**

> 이번 과제에서 가장 중요하게 보는 성능 지표는 무엇인가요? 문자·의미 해석 정확도 외에 잘못 확정한 작업이나 조건의 비율, 사람 확인 없이 처리한 비율, 확인 시간도 함께 제시하려고 합니다. 어떤 평가 사례와 정답 기준을 사용하는 것이 적절할까요?

**이어 물을 말**

> 정보가 부족한 경우 확인을 요청하는 결과는 어떻게 평가하나요? 기대하는 자동 처리 수준과 별도로 측정해야 할 오류 유형이 있나요? 맥락을 사용했을 때와 사용하지 않았을 때를 같은 사례로 비교해도 될까요?

**질문하게 된 배경** — 하위 E2·E3는 ‘조용한 오류 0일 때 무인 처리율’과 보류 평가를 묻는다. 하지만 일부 평가에서 오류가 발견되지 않았다는 결과만으로 현장 오류가 없다고 보장할 수는 없다.

**왜 필요한가** — 항상 보류해서 오류만 줄인 시스템과, 실제 업무를 정확히 처리하는 시스템을 구분하기 위해서다. 비교 조건과 전체 사례 수도 함께 필요하다.

**답변에서 확보할 것** — 평가 단위, 정답 검토 방식, 데이터 분리 기준, 주요 오류, 자동 처리·보류의 정의, 목표 수준.

**답변 후 결정** — 아래처럼 분모가 드러나는 지표로 평가안을 만든다. 공식 평가 방식은 담당자 답변 후 확정한다.

| 제안 지표 | 기록 방법 |
|---|---|
| 의미 해석 정확도 | 맞힌 항목 수 / 평가 항목 수. 보류 항목의 처리도 명시 |
| 자동 확정 결과의 오류 | 자동 확정 중 오류 건수 / 자동 확정 건수 |
| 자동 처리율 | 사람 확인 없이 결과를 확정한 건수 / 전체 평가 건수 |
| 확인 요청률 | 사람에게 확인을 요청한 건수 / 전체 평가 건수 |
| 전체 처리시간 | 촬영·시스템 처리·사람 확인·대기를 포함한 시간과 사례 수 |
| 맥락 사용 효과 | 동일 사례에서 사용 전후의 정답·오류·보류 건수, 잘못된 맥락 사례의 결과 |

자동 확정 사례가 없으면 그 집단의 오류율은 계산할 수 없다고 적는다. 시험에서 오류가 없었다면 ‘평가한 자동 확정 사례 중 관측 오류 0건’과 사례 수를 함께 쓰고, 현장 무오류나 무인 운용이 검증됐다고 표현하지 않는다.

원문 연결: 하위 E2·E3, 상위 Q2.
