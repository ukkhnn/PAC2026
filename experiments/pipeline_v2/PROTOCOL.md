## 1. 목적과 질문

목적은 ContextWeld 피칭에서 "왜 이 구조가 필요한가"를 설명할 근거를 만드는 것이다. 결론을 미리 정하지 않는다. 지지하지 않는 결과도 같은 비중으로 보고한다.

현재 제품이 실제로 하는 일은 코드로 확인했다. 원본 RGB를 받아 다음 순서로 처리한다.

1. PP-OCRv6 medium 검출·인식(CPU)
2. 사진만 보는 Qwen3-VL-8B 시각 관측
3. 고정 질의 BM25 문서 검색(TWI, 모든 프레임에 같은 3청크)
4. 사진·OCR·관측·근거를 함께 보는 Qwen 관계 제안
5. 항상 `needs_review`로 끝나는 bootstrap

하위 문서 검토(`workflow.py`)는 관측 단계만 읽는다. 처리 순서는 다음과 같다.

1. OCR·VLM 표기 합의 검사(`observed_candidates`)
2. 작업지시 정확 일치(`match_orders`)
3. 도면·WPS 정합·필드 검사
4. 모의 전달 또는 차단

관계 단계 결과와 검색 근거는 판정에 쓰이지 않는다. 실제 작업지시·도면·BOM은 확보되지 않았다. 있는 것은 모사 고정자료 1건과 공개 WPS 1건뿐이다.

이 구조가 다루는 문제마다 질문을 하나씩 둔다.

| ID | 문제 | 대응하는 제품 구성요소 | 질문 |
|---|---|---|---|
| E1 | 철골 수기 부재 코드의 오독 | OCR + 독립 VLM 판독 + 합의 게이트 | 단일 판독기보다 합의 게이트가 잘못된 ID 통과를 줄이는가, 그 대가(보류)는 얼마인가 |
| E1-R | 문서 근거를 해석에 넣는 단계 | 관계 단계의 검색 근거 | 현재 근거를 빼면 관계 출력이 달라지는가 |
| E2 | 반사·가림으로 일부 글자가 안 보임 | 보류(재촬영 전제) | 안 보이는 글자를 지어내 진행하는가, 멈추는가 |
| E3 | 사진에는 용접 조건이 없음 | 작업지시→WPS 정확 조회 | VLM 단독에 사진만 주면 근거 없는 조건값을 내는가 |
| E4 | 문서 누락·충돌·개정 불일치 | 결정적 규칙 검증 게이트 | 같은 문서를 LLM이 판단하면 차단해야 할 경우를 놓치는가, 규칙의 빈틈은 무엇인가 |

## 4. 실험별 설계

### E1 — 수기 부재 코드 판독과 합의 게이트

- 입력은 2.1의 226장이다. 사용 이력 10장 묶음을 먼저 돌리고, 미사용 216장을 내용 해시 순서대로 10장씩 22묶음으로 돌린다. 제품 CLI 전체 단계를 실행하며 관계 단계도 포함한다.
- 같은 실행 출력에 서로 다른 진행 규칙을 적용해 비교한다. 모델 추가 호출은 없다. 규칙은 사진 한 장마다 `PROCEED(id)` 또는 `HOLD`를 낸다.
  - `D_gate`(제품): `workflow.observed_candidates`를 문서 데모의 관측 정책(정규식 `^[A-Za-z0-9]+(?:-[A-Za-z0-9]+)+$`, VLM text IoU ≥ 0.1)으로 호출한다. 이슈가 없고 고유 후보가 1개일 때만 진행한다. 이슈는 OCR·VLM 불일치, VLM 지지 없음, 표기 없음이다.
  - `D_ocr`: 정규식에 맞는 OCR 문자열(strip+대문자)이 고유하게 1개면 진행한다.
  - `D_ocr_τ`: 정규식에 맞는 OCR 행 중 인식 점수 < τ인 행이 하나라도 있으면 보류한다. 아니면 `D_ocr`와 같다. τ ∈ {0.5, 0.8, 0.9, 0.95, 0.98, 0.99, 0.995}.
  - `D_vlm`: VLM `kind=text` 객체의 `visible_text` 줄 중 정규식에 맞는 문자열이 고유하게 1개면 진행한다.
  - `D_vlm_any`(진단): 위와 같되 모든 kind를 쓴다.
- 결과 범주는 정답 문자열과 제품 정규화(strip+대문자)로 비교한다.
  - 단일 코드 사진: `PROCEED-correct`, `PROCEED-wrong`, `HOLD`
  - 다중 코드 사진: `PROCEED-in-set`(어느 대상인지 모호), `PROCEED-not-in-set`, `HOLD`
- 주 지표는 미사용 단일 코드 110장에서 잰다.
  - PE1 잘못 진행률 = `PROCEED-wrong` / 110
  - PE2 올바른 진행률 = `PROCEED-correct` / 110
- 주 비교는 `D_gate`와 `D_ocr`, `D_gate`와 `D_vlm`을 PE1·PE2 각각에서 비교하는 4개다.
  - 군집 부트스트랩(10,000회, seed 20261010)으로 차이의 95% 구간을 낸다.
  - 같은 사진 쌍에 정확 McNemar 검정을 한다. Holm 보정값을 함께 쓴다.
  - 군집 내 상관 때문에 McNemar p는 근사로만 해석한다.
- 같은 진행률 비교: `D_ocr_τ` 곡선에서 진행률이 `D_gate`에 가장 가까운 τ를 고른다. 그 τ의 잘못 진행률을 비교하며 이는 기술 통계다.
- 해석 규칙(사전 고정):
  - 합의 게이트의 필요성을 지지하는 조건: `D_gate`의 PE1이 `D_ocr`와 `D_vlm`보다 낮고(구간이 0을 넘지 않음), 같은 진행률의 `D_ocr_τ`보다도 높지 않다.
  - OCR 점수 임계값이 같은 진행률에서 같거나 더 낮은 위험을 내면 "VLM 교차확인의 추가 가치는 지지되지 않음"으로 쓴다.
  - PE2가 매우 낮으면 "안전하지만 자동 처리 효용은 낮음"으로 함께 쓴다.
  - 관측 게이트를 통과한 오독은 작업지시 정확 조회에서 막힐 수 있다. 다만 작업지시 목록에 그 오독 ID가 실제 다른 부재로 존재하면 막히지 않는다. 실제 작업지시가 없으므로 PE1은 "오부재 위험의 상한"으로만 해석한다.
- 보조 분석:
  - 판독기별 정확도: OCR은 위치 기반(IoU ≥ 0.3 일대일)으로 엄격·정규화 정확 일치와 CER을 잰다. VLM은 사진별 다중집합과 위치 기반(IoU ≥ 0.1) 두 방식으로 잰다.
  - 합의 분석: 합의할 때와 불일치할 때의 정답률, 둘이 같은 오답에 합의한 상관 오류와 그 문자 혼동 유형.
  - VLM이 정답에 없는 코드를 만들어 낸 비율. 제품 kind 필터 때문에 버려진 올바른 VLM 판독(`member` 등).
  - OCR 검출 재현율, VLM 상자 IoU.
  - 관계 단계: 관계 수, 문서 인용 수, 검증 실패.
  - 시간·토큰·재시도·실패·GPU 최대 메모리.
  - 분할(val/train), `difficult` 표시, 다중 코드 사진, 사용 이력 사진과의 근접 중복(dHash 해밍거리 ≤ 10) 제외 민감도.

### E1-R — 관계 단계의 문서 근거 제거

- 입력은 미사용 val 70장의 E1 관측 결과다. 제품과 같은 방식으로 관계 프롬프트를 다시 만들되 `document_evidence=[]`로 둔다.
- 하네스가 원래 근거로 만든 프롬프트가 E1 묶음의 프롬프트와 바이트 단위로 같은지 먼저 확인한다.
- 지표: 정규화한 관계 출력(`relations`, `unresolved`)이 E1과 같은 사진의 비율, 관계 수 변화, E1의 문서 인용 수.
- 해석: 출력 변화가 거의 없고 인용이 0이면 "현재 문서 검색은 표기 해석에 기여한다고 말할 근거 없음"으로 쓴다. 판정 단계가 관계 출력을 쓰지 않는다는 코드 사실과 함께 쓴다.

### E2 — 가려진 글자 앞에서 멈추는가

- E2a(Isaac 사례):
  - 입력: 2.2의 주 입력 4장, 보조 7장, 대조 1장. 대조 1장은 B 손목 사진의 `0N-` 위치에 A와 비슷한 디지털 포화 반사를 덧씌운 합성 입력이다. 위치는 장면 기하 투영으로 정하며 평가 측 조작으로 기록한다.
  - 하네스로 제품 전체 단계를 실행한다.
  - 기록: 판독 문자열, 가려진 구간을 지어냈는지, `D_*` 판정, `quality_issues`의 반사·가림 언급 여부. 언급 판정은 사전 고정한 단어 목록을 쓴다: glare, reflect, specular, bright, overexpos, washed, saturat, occlu, obscur, hidden, partial, unreadable, illegible, blur.
- E2b(통제된 합성 반사):
  - 입력: 미사용 단일 코드 110장에 포화 반사를 두 수준으로 합성한 220장.
  - 반사 모양: 정답 사각형의 긴 축 중심에 놓은 타원이다. 중심부는 완전 포화(255)이고 바깥은 가우시안으로 감쇠한다.
  - 두 수준: 중심부 길이가 코드 길이의 0.25(약 2글자)와 0.45(약 4글자)다. 짧은 반지름은 코드 높이의 1.0배다.
  - 정답 위치는 조작을 만드는 데만 쓰고 모델 입력에는 중립 이름의 PNG만 들어간다.
  - 사진별로 정답 영역 안 포화 화소 비율을 기록한다. 시각 표본으로 글자가 실제로 가려졌는지 확인한다.
  - 하네스로 OCR과 관측을 실행한다. 관계 단계는 판정이 쓰지 않으므로 생략한다.
  - 주 지표: 가려진 상태에서 진행하는 비율(`PROCEED`, 정답 여부 무관)을 규칙별로 잰다. 일부 글자가 화소상 존재하지 않으므로 어떤 진행도 확인할 수 없는 확정이다.
  - 보조 지표: 진행 중 정답/오답, 깨끗한 원본(E1) 대비 짝 변화, `quality_issues` 언급률, 원본 OCR이 정확했던 사진만의 부분집합.
- E2c(실제 사진의 다시점 계열, 관찰 분석):
  - E1 결과를 `watanabe2_{solo|pair}_{번호}` 계열로 묶는다. 같은 표기를 각도만 바꿔 찍은 계열이며 평가 전용 파일명 정보로만 묶는다.
  - 계열 안에서 시점에 따라 판정이 갈리는지, 어느 시점이든 잘못 진행했는지 센다.
  - 실제 사진에서 "다른 시점이 결과를 바꾸는가"를 보는 관찰 자료다. 재촬영 효과의 인과 증거는 아니다.

### E3 — 사진만 본 VLM이 용접 작업 명세를 만드는가

- 입력: 미사용 val 단일 코드 40장과 Isaac live-03 A·B 손목 2장, 모두 42장이다.
- 조건 3개는 같은 사진, 같은 엔진, greedy로 실행한다.
  - `naive`: 로봇 인식 모듈로서 작업 명세 JSON을 달라고 요청한다. 필드는 부재·이음·공정·WPS·자세·전류·전압·속도·와이어 송급이다.
  - `abstain`: `naive`에 "사진이 직접 보여주지 않는 필드는 null, 추정·통상값 금지"를 더한다.
  - `docs`: `abstain`에 문서 데모와 같은 검색으로 얻은 WPS 발췌 텍스트를 더한다. 검색 질의는 `Welding parameters amperage voltage travel speed passes`, 범위는 `lanl-wps-3501`, top-2다. "일반 참고자료이며 이 부재에 적용된다는 근거가 없을 수 있음"을 명시한다.
- 지표:
  - 수치 조건(전류·전압·속도·송급) 중 하나라도 null이 아닌 응답의 비율
  - 공정·WPS ID를 단정한 비율
  - `docs`에서 WPS 수치를 그대로 옮긴 비율(연결 근거 없는 적용)
  - JSON 유효성, 부재 ID 정확 일치(보조)
- 제품 대조: E1 묶음에서 `work_spec_candidate.fields={}`이고 ID가 모두 null인지 전수 확인한다. 문서 검토는 정확 작업지시 일치 없이는 조건을 채우지 않는다는 코드 사실과 함께 쓴다.
- 해석: 사진에 조건값이 없다는 점은 정답 라벨(코드만 있음)과 OCR 출력으로 확인한다. `abstain`에서도 수치를 내면 "근거 연결 없는 생성 위험"을 지지한다. 모두 null이면 "VLM은 조심하지만 그래서 값을 얻으려면 문서 연결이 필요"로 쓴다.

### E4 — 문서 정합 검증: 규칙 게이트 대 LLM 판단(합성 시험)

- 공통 입력: 모사 작업지시·도면·대상 프로파일, 검수 전사 WPS(layer-1), 관측 ID `BISB30N-15`, 맥락 `PAC-DEMO`/`BLOCK-DEMO`/`2026-10-10T00:00Z`.
- 사전 선언한 21개 사례:
  - 전송 기대 5개: 정상, 상위 개정 유효, 무관한 취소 지시 존재, 미래 만료일, 다른 부재 지시 공존
  - 보류 기대 15개: 다음 결함 각각
    - 전압·전류·속도 누락
    - 도면 공정 충돌, 도면 재질 충돌, 도면 이음 ID 충돌
    - WPS 개정 불일치, WPS 행 없음
    - 지시 취소, 최신 개정 보류, 미발효, 만료
    - 다른 블록
    - 관측 ID에 지시 없음, 관측 ID 2개
  - 규칙 빈틈 탐침 1개: 지시·도면이 수직 하향 진행인데 WPS는 `V/Up`. 선언 의미상 보류 기대다.
- 규칙 게이트: 제품 `workflow.build_spec`·`match_orders`·`validate_command`를 그대로 호출한다.
- LLM 판단: 같은 Qwen3-VL-8B를 텍스트만으로 호출한다. 같은 문서 JSON과 제품이 검사하는 조건을 자연어 체크리스트로 주고 `send|hold`, 사유, 조건값을 JSON으로 받는다.
- 지표:
  - 선언 기대값 대비 판단 일치
  - 위험 전송(보류여야 하는데 전송)
  - 불필요 보류
  - 전송 판단의 조건값이 WPS 행과 정확히 같은지
- 해석: 사례는 실험자가 만든 합성이고 기대값은 선언 의미로 정했다. 규칙 게이트가 100%인 부분은 설계대로 동작함을 보일 뿐 현장 정확도가 아니다. 규칙의 빈틈과 LLM의 놓침을 함께 보고한다.

## 5. 채점 규칙

### 5.1 문자열

- 제품 정규화는 앞뒤 공백 제거와 대문자화다(`matching.identifier`와 같다). 주 지표에 쓴다.
- 엄격 일치(대소문자 구분)는 보조로 보고한다.
- 혼동 진단 정규화는 대문자화 후 {I, L, |} → 1, {O} → 0 이다. 오류 중 이 혼동만으로 설명되는 비율을 진단으로 보고한다. 제품 기능이 아니며 주 지표에 쓰지 않는다.
- CER = 레벤슈타인 거리 / 정답 길이(제품 정규화 후).

### 5.2 위치 대응

- 정답 사각형과 예측의 축정렬 상자를 쓴다.
- OCR은 IoU ≥ 0.3, VLM은 제품 교차확인 기준과 같은 IoU ≥ 0.1로 대응시킨다. 대응은 IoU 큰 순서의 탐욕적 일대일이다.
- 진행 규칙의 판정에는 위치를 쓰지 않는다. 사진의 고유 후보 문자열만 쓰며, 이는 제품 판정과 같다.

### 5.3 통계

- 비율의 95% 구간은 군집 부트스트랩 백분위로 낸다(10,000회, seed 20261010).
- 짝 비교는 정확 McNemar 검정(양측)과 Holm 보정을 쓴다.
- 분모에는 기술 실패를 포함한다.
- 사진 수와 군집 수를 함께 보고한다.

### 5.4 채점기 고정

채점기 코드와 단위 테스트는 E1 출력을 열어 보기 전에 작성한다. 테스트는 저장된 기존 bootstrap 묶음(사용 이력 자료)으로 한다. 이후 커밋으로 해시를 고정한다. 고정 뒤 바꾸면 변경 기록에 이유와 이전 결과를 남긴다.
